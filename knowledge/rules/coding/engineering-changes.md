# 소프트웨어 변경·검증 기준

## 적용 범위와 기준의 위치

코드·연동·구조 변경과 그 테스트·리뷰·병합에 적용한다. 해당 작업의 절만 사용하며 작은 수정에 전체 절차를 형식적으로 실행하지 않는다.

맥락 확인, 변경 범위, 일관된 재구성과 연결 검증은 [공통 작업 원칙](../../../AGENTS.md#모든-활용-에이전트의-공통-작업-원칙)을 따른다. UI/UX 품질과 검수 기록은 [UI/UX 통합 지침](../design/universal-uiux.md)을 따른다. 이 문서는 엔지니어링 고유의 판단과 실행 방법만 다룬다.

## 1. 기존 구현 활용·공통화·모듈 경계

- 필요한 책임을 이미 가진 모듈·공개 API·유틸을 먼저 확인한다. 같은 기능을 새 모듈이나 유틸로 다시 만들지 않는다.
- 모듈 경계는 역할과 책임 → 필요한 관계와 인터페이스 → 이름 순으로 판단한다. 기존 모듈에 책임을 모을 수 있는지 먼저 비교하고, 정상적인 모듈 간 API 의존은 유지한다.
- 새 모듈 추출은 실제 책임 혼재·변경 위험·개발 충돌 등 구체적 유지보수 문제를 해결할 때 선택한다. 코드량·파일 길이·파일 수 감소 자체를 목표로 삼지 않는다. 효과가 불명확한 분리는 현재 구조를 유지한다.
- 같은 업무 규칙은 공통 관리를 기본안으로 검토한다. 한쪽 규칙의 수정이 다른 쪽에도 필요한지 확인하며, 코드 모양만 비슷한 다른 업무 의미는 결합하지 않는다. 정책값만 다르면 같은 알고리즘에 정책을 별도로 공급하는 방식을 우선한다.
- 제품 목적·플랫폼·상호작용 때문에 달라져야 하는 구현은 분리할 수 있다. 담당자나 저장소가 다르다는 사실만으로 같은 업무 규칙의 중복을 정당화하지 않는다. 공통 규칙은 명확히 표현하되 현재 필요한 변형만 추상화한다.
- 실험 중 임시 중복은 정식 도입 전에 정리한다. 마이그레이션·롤백을 위한 구·신 구현의 공존에는 전환 종료와 복귀 보존에 따른 제거 조건을 둔다. 특정 아키텍처·모노레포·디자인 패턴을 일괄 강제하지 않는다.

## 2. 변경 계약·연동 책임·구현 인계

- 계획과 작업 명세는 이미 제공되는 기능, 재사용할 구현, 이번에 추가·변경할 부분을 구분한다. 기존 기능을 신규 작업처럼 서술해 재구현을 유도하지 않는다.
- 여러 repo를 함께 변경하면 공통 인터페이스의 필드·필수/선택 조건·입출력·오류 계약과 repo별 변경 책임을 같은 설계 원본에서 연결한다. 이미 정한 명세를 새 문서로 중복 관리하지 않는다.
- 리팩터링·관측·테스트 지원 변경에서는 보존해야 할 계약을 영향 범위에 맞게 확인한다. 반환값·원본 Response/Error·throw, 콜백 순서·재시도 조건과 지연·취소·병렬 실행, 트랜잭션·잠금·멱등성·조직 경계 중 관련된 것을 대조한다. 모든 항목을 매 작업의 의무 검사로 만들지는 않는다.
- 업무 결과를 바꾸는 기능·정책 변경과 동작을 보존하는 구조 변경을 구분한다. 관측이나 자동화의 편의를 위해 업무 계약을 임의 변경하지 않는다.
- 구현 인계에는 대화 맥락 없이 목표·계약·제약·담당 범위·기준 자료·완료 조건을 판단할 정보를 남긴다. 확정된 조건은 분명히 하되, 아직 정하지 않은 내부 구현까지 고정해 상황에 맞는 공학적 선택을 막지 않는다.

## 3. 테스트 작성·수정·삭제

- 테스트 개수를 억지로 줄이거나 늘리지 않는다. 실제 제품 계약과 사용자 동작을 검증하는 데 필요한 만큼 작성한다.
- 같은 의미를 반복하는 검사는 정리하되, 서로 다른 회귀 위험을 방어하는 테스트는 유지한다. 제거할 때는 어떤 계약·위험의 검증이 남는지 확인한다.
- 테스트를 위해 제품 코드를 불필요하게 확장하거나 업무 구현을 복제한 테스트용 구조를 만들지 않는다. 업무 흐름 자동화는 실제 제품에서 사용하는 업무 코드를 호출한다.
- 외부 의존성의 모의 처리와 검증 대상 업무 로직의 복제는 다르다. 모의 결과를 실제 연동 성공으로 해석하지 않는다. 필요한 제품 코드 변경이나 테스트 경계 분리를 전면 금지하는 기준은 아니다.
- 실행 범위는 변경 영향과 프로젝트 기준으로 정한다. 테스트 수 감축 목표나 영향 범위 밖 검사의 일괄 실행 금지를 뜻하지 않는다.

## 4. 실패의 원인과 변경 귀속

1. 정확한 기준·후보 커밋과 diff, 실패한 명령·입력·환경·의존성·DB 초기 조건을 확인한다. 원격 CI 결과와 로컬 재현을 구분한다.
2. 변경 코드와 실패 경로를 대조하고, 필요하면 기존 작업을 건드리지 않는 별도 공간에서 같은 조건으로 기준 커밋과 비교 실행한다. 실패 파일이 diff에 없다는 이유만으로 기존 실패라고 판정하지 않는다. 기준에서도 실패한다는 사실만으로 같은 원인이라고 단정하지 않는다.
3. 이번 변경으로 발생·악화된 실패, 기준에서도 확인된 기존 실패, 근거 부족으로 미확정인 실패를 구분한다. 비교 실행·오류 경로·코드 근거를 종합한다. 기준 재현이 불가능하다는 이유만으로 일률적으로 미확정 처리하지 않으며, 다른 증거까지 고려해도 귀속 근거가 부족한 경우 미확정으로 남긴다.
4. 이번 변경에 귀속된 실패는 승인 범위에서 해결하고 다시 검증한다. 기존 실패는 무관한 수정으로 확대하지 않고 근거와 남은 차단 사항을 보고한다. 동일 원인의 실패는 묶되 영향받는 검사·경로를 누락하지 않는다.

기존 실패라는 판정은 CI 통과나 merge 가능을 뜻하지 않는다. 프로젝트의 실제 merge 조건을 별도로 확인하고 검사 우회나 기대값 완화로 성공 처리하지 않는다.

## 5. 브랜치 병합·충돌 해결

1. 허용된 기준·대상 브랜치, 각 브랜치의 변경과 작업 트리의 미커밋 변경을 구분한다.
2. 충돌한 부분의 양쪽 목적과 연결된 호출·사용처를 읽고 필요한 의도를 통합한다. 한쪽 파일이나 변경을 통째로 선택하는 것으로 충돌 해결을 대신하지 않는다.
3. i18n은 양쪽 번역 추가·수정을 확인한다. 같은 키의 의미가 충돌하면 의미를 확인해 해결한다. rename·파일 교체는 이전 파일의 다른 변경도 추적해 새 위치에서 필요한 동작이 보존되는지 확인한다.
4. 기준 브랜치 대비 최종 diff에서 이미 반영된 변경의 중복 유입을 확인하고 통합 영향을 검증한다. 충돌 표시 제거만으로 완료하지 않는다.

함께 만족시킬 근거가 없는 요구는 한쪽을 임의 폐기하지 않고 필요한 결정을 알린다. 이 절은 commit·push·merge·배포 권한을 추가하지 않는다.

## 6. 검증 자산의 재사용·관리

- 기존 테스트 체계와 E2E 시나리오·실행 자산을 먼저 확인하고 재사용한다. 같은 검증을 위한 독립 스크립트·fixture·테스트 파일을 필요 없이 추가하지 않는다.
- 일회성 검수 보고서·이미지·생성 스크립트와 지속 유지할 회귀 테스트를 구분한다. 반복 사용할 실행 자산은 유지보수 대상으로 다루고, 저장·버전 관리 범위는 프로젝트 기준과 현재 요청에서 정한다. 모든 E2E 리소스를 PR에서 일괄 제외하지 않는다.
- 사용자 흐름을 검수 보고서로 전달할 때는 [UI/UX 지침의 최소 기록](../design/universal-uiux.md#최소-기록)을 사용한다. 별도 보고서·PDF·스크린샷을 모든 작업에 강제하지 않는다.

## 판단 근거와 일반화의 범위

소유자가 여러 개발 작업에서 직접 요구한 제품 계약 중심 테스트, 실제 업무 코드 호출, 병합 시 양쪽 의도 보존, 실패의 변경 귀속을 기존 기준에서 통합했다. 모듈 분리의 실익, 기존 기능과 신규 작업의 구분, 관측 변경의 구체적 보존 계약도 사용자 지시들을 교차 검토해 보완했다.

특정 프론트엔드 통합 논의에서 합의한 공통화·임시 중복 기준은 저장소 구조와 분리해 적용했다. 인계 명세의 구체성 및 검증 자산 관리는 자기 완결성·구현 선택의 여지, 일회성 자료·유지할 테스트라는 서로 다른 요구를 함께 만족하도록 정리한 표준안이다. 소유자가 이 통합·보완안을 승인했다. 특정 프로젝트의 브랜치·배포·데이터 보존 정책까지 공통 의무로 확대하지 않으며, 비공개 원문과 업무 식별자는 포함하지 않는다.
