# 레퍼런스 우선 UI/UX 설계 지침

> **문서 상태:** 핸드북을 참조하는 에이전트도 이 원칙을 따르도록 한 소유자의 요청에 따라 활성화한 실행 규칙이다. 적용 범위에 해당하는 설계·구현 작업에서는 기본 규칙으로 확보하고 따른다.

## 적용 상황

신제품의 초기 시안, 와이어프레임, 인터랙티브 프로토타입, MVP, 출시용 UI 구현과 기존 제품의 UI/UX 개선에 적용한다. 디자이너뿐 아니라 화면이나 상호작용을 만드는 코딩 에이전트에도 해당한다.

목표는 **바퀴를 다시 발명하지 않고, 적합한 기존 제품의 UI와 동작을 잘 가져와 빠르게 만들고 시장에서 확인하는 것**이다. 백지에서의 독창적 설계를 기본값으로 삼지 않는다.

## 기준

### R01. 시안 작성보다 레퍼런스 확인을 먼저 한다

- 현재 사용자의 목표, 핵심 과업, 서비스 성격, 주요 기기와 제약을 짧게 파악한다. 기존 제품이라면 적용 중인 디자인 시스템과 실제 화면도 확인한다.
- 같은 문제를 해결하는 경쟁 서비스나 인접 제품을 찾아 확인한 뒤 시안을 작성한다. 사용자가 기준 제품을 지정했다면 먼저 확인한다.
- 에이전트의 기억, 익숙한 템플릿, 생성 가능한 수준만으로 만든 화면을 레퍼런스 기반 시안이라고 보고하지 않는다. 제품명을 나열하는 것만으로 확인을 대신하지 않는다. 에이전트가 특정 도구나 구현 방식에 익숙하지 않다는 이유만으로 기준 제품의 경험을 임의의 범용 화면으로 대체하지 않는다.

### R02. 적합한 제품을 기준안으로 선정한다

- 시각적 유행이나 유명세보다 사용자 과업, 정보 구조, 사용 맥락과의 유사성을 우선한다. 시장 사용 사례, 공식 제품 자료 등 확보한 근거와 적용상의 차이를 함께 본다.
- 핵심 흐름을 일관되게 가져올 주 기준 제품을 정한다. 보조 레퍼런스는 주 기준에서 해결하지 못한 부분에 사용하며, 여러 제품의 예쁜 부분만 섞어 조작 문법을 깨뜨리지 않는다.
- 적합한 답을 찾았다면 조사만 계속하지 않고 재현으로 넘어간다. 후보 수나 조사 분량을 형식적으로 채우지 않는다.

### R03. UI와 동작을 함께 충실히 재현한다

- 적합한 경쟁 제품의 화면 구조와 상호작용을 권리·접근 조건이 허용하는 범위에서 충실히 재현하는 것을 기본안으로 삼는다. 단순한 영감 수집이나 추상적인 패턴 참고로 축소하지 않는다. 변경은 R04의 구체적인 이유가 있을 때 필요한 부분에 한정한다.
- UI는 정보의 순서·밀도·배치·시각적 위계·컴포넌트·반응형 구성을 확인한다. 동작은 진입점·단계·기본값·입력·선택·화면 전환·피드백·복구 흐름을 확인한다.
- 필요한 기본·로딩·빈 화면·오류·성공·비활성 상태와 키보드·포커스 동작도 대상으로 삼는다. 정적 화면만 보고 전체 동작을 확인했다고 쓰지 않는다.
- 사용할 수 있는 기존 디자인 시스템과 컴포넌트가 있다면 재사용한다. 기존 제품에서는 외부 레퍼런스의 흐름을 현재 시스템의 표현 문법에 맞추고, 필요 없이 별도 시스템을 만들지 않는다.

### R04. 새로 설계하는 쪽이 변경 이유를 설명한다

- 질문의 기본값은 ‘어떻게 새롭게 만들까’가 아니라 ‘이미 있는 답을 가져오면 안 되는 이유가 있는가’이다.
- 차별화가 필요 없는 부분은 유지한다. 에이전트의 취향, 독창성 과시, 막연한 브랜드 차별화를 이유로 익숙한 흐름을 바꾸지 않는다.
- 핵심 제품 가치, 사용자 맥락, 접근성, 안전, 플랫폼 또는 구현 제약 때문에 필요한 부분만 수정한다. 무엇을 바꾸고 왜 바꾸는지 기록한다.
- 적합한 레퍼런스가 없으면 인접 제품의 검증 가능한 패턴을 조합하고 미확인 부분을 설계 가설로 표시한다. 억지로 부적합한 제품을 복제하지 않는다.

### R05. 재현의 속도를 실제 출시와 검증으로 연결한다

- 초기 목표는 전체 경쟁 제품의 복제품이 아니라, 핵심 사업 가설을 확인할 수 있는 최소한의 일관된 경험이다. 필요한 흐름을 충실히 재현하되 무관한 기능까지 만들지 않는다.
- 경쟁 제품을 따랐다는 이유로 우리 결과물의 동작·사용성을 검증 완료로 판정하지 않는다. 핵심 과업을 실제로 실행해 화면·상태·결과를 확인하고, 프로토타입의 모의 처리와 실제 연동을 구별한다.
- 사용자 테스트와 시장 반응은 실제 수행·관찰한 경우에만 근거로 보고한다. 레퍼런스 채택은 빠르게 출발하는 방법이지 우리 제품의 성공을 보장하는 증거가 아니다.
- 출시 속도를 이유로 필수 접근성·안전·오류 복구를 생략하지 않는다. 외부 게시와 배포는 현재 요청에서 허용한 범위 안에서만 수행한다.

## 에이전트의 실행 순서와 기록

1. **과업과 범위를 정한다.** 만들 경험, 검증할 가설, 기존 시스템과 제약을 짧게 정리한다.
2. **레퍼런스를 확인한다.** 실제 제품을 조작해 흐름을 확인한다. 접근이 어려우면 공식 데모·문서·영상·사용자가 제공한 화면을 이용하고, 근거 유형과 확인하지 못한 범위를 남긴다.
3. **기준안을 선택한다.** 주 기준 제품과 선정 이유, 가져올 화면·동작, 필요한 변경을 정한다.
4. **핵심 경험을 재현한다.** 확인한 UI와 동작을 기본안으로 만들고, 미확인 부분은 가설로 구별한다.
5. **대조하고 보고한다.** 레퍼런스와 구현을 비교하고 핵심 흐름을 실행한 결과, 차이, 남은 제약을 기록한다.

작업 규모에 비례해 아래 내용을 설계 문서 또는 결과 보고에 남긴다. 별도 장문의 조사 보고서를 만들 필요는 없지만, 레퍼런스와 변경·검증 근거는 추적할 수 있어야 한다.

| 기록 항목 | 포함할 내용 |
| --- | --- |
| 사용자 과업과 범위 | 목적, 핵심 흐름, 기기·환경, 이번에 만들지 않는 범위 |
| 레퍼런스와 선정 이유 | 서비스명, 확인한 URL, 확인일, 과업과의 적합성 |
| 관찰 근거와 한계 | 실제 조작·공식 데모 등 근거 유형, 확인한 화면·상태·동작, 미확인 부분 |
| 재현과 변경 | 그대로 가져올 UI·동작, 바꿀 부분과 구체적인 이유 |
| 실제 결과 | 구현·렌더링·흐름 실행 결과, 모의 처리, 미확인 사항과 다음 검증 |

## 예외와 조건

- **레퍼런스 접근 불가:** 로그인·유료 접근·지역 제한 등으로 확인하지 못하면 그 사실을 명시한다. 우회 권한을 가정하지 않고 공개 자료나 다른 적합한 제품을 활용한다. 핵심 동작의 근거를 확보할 수 없다면 해당 부분을 임시 가설로 표시하고 필요한 자료를 요청한다.
- **즉시 시안 요청 또는 조사 제한:** 짧은 요청이라는 이유로 확인을 생략하지 말고 핵심 흐름에 한정해 조사한다. 사용자가 외부 조사 금지 등으로 범위를 제한하면 그 지시를 따르되, 결과를 미검증 가정 기반 시안으로 명시한다.
- **시장 검증과 관찰의 구분:** 널리 쓰이는 제품이라는 사실, 특정 UI를 관찰한 사실, 그 UI의 효과가 실증됐다는 주장은 서로 다르다. 공개 근거나 실제 테스트 없이 효과가 검증됐다고 단정하지 않는다. 실증 자료가 없다는 이유만으로 적합한 레퍼런스의 활용을 모두 보류할 필요도 없다.
- **권리와 신뢰:** UI·동작의 참고·재현과 타사의 코드·문구·로고·이미지·데이터의 무단 복제는 구별한다. 사용할 자산의 권리·이용 조건을 확인하고, 타사로 오인하게 하는 표현이나 기만적 흐름은 가져오지 않는다.
- **기준 충돌:** 현재 요청과 대상 프로젝트의 명시적 지침을 먼저 따른다. 이 문서는 [범용 UI/UX 표준 지침](universal-uiux.md)의 결과 품질 기준을 대체하지 않는다. 두 문서의 활성 상태를 각각 확인한다.

## 적용 예시

- **신제품 프로토타입:** 예약 서비스의 핵심 가설을 확인하려면 유사한 예약 제품에서 날짜·시간 선택부터 예약 완료까지 확인하고 재현한다. 우리 서비스에 필요한 조건만 변경한다. 차별화를 위해 새로운 달력 조작법부터 고안하지 않는다.
- **기존 제품 개선:** 목록·상세 화면을 개선할 때 현재 컴포넌트를 유지하면서 적합한 경쟁 제품의 탐색 흐름을 가져온다. 제품 전체를 다른 스타일로 바꾸지 않는다.
- **피해야 할 결과:** 서비스명 몇 개만 적은 뒤 관찰 근거 없이 범용 대시보드 템플릿을 만들고 ‘경쟁 서비스의 검증된 UX를 적용했다’고 보고하는 것.

## 적용 확인

- 시안 전에 실제로 확인한 레퍼런스 또는 확인을 제한한 조건이 기록됐는가?
- 서비스의 과업에 맞는 주 기준 제품과 선정 이유가 있는가?
- UI뿐 아니라 핵심 동작·상태를 가져왔고, 관찰하지 못한 부분은 구별했는가?
- 새로 설계하거나 바꾼 부분에 구체적인 이유가 있는가?
- 조사·구현 범위가 최소 핵심 경험과 빠른 시장 검증에 집중돼 있는가?
- 결과물의 실제 실행 결과와 사용자·시장 검증의 미수행 범위를 구별했는가?

확인하지 못한 항목은 미확인으로 남긴다. 문서 작성이나 레퍼런스 선정만으로 실제 시안·제품의 적합성을 판정하지 않는다.

## 판단 근거

기존 제품의 익숙한 UI와 동작을 출발점으로 삼고, 차별화가 불필요한 부분의 재설계를 줄여 출시와 시장 검증을 앞당기려는 소유자의 제품 설계 방향을 실행 기준으로 구체화했다. AI가 자신의 기억과 생성 능력에만 의존해 임의의 시안을 만드는 문제를 방지하기 위한 기준이다.

특정 경쟁 서비스의 성과를 조사해 도출한 연구 결과나 사용자 테스트 결과가 아니다. 이 문서는 작업 방식에 대한 판단 기준이며, 개별 레퍼런스의 적합성과 실제 제품의 결과는 각 작업에서 확인한다. 비공개 대화 원문은 포함하지 않는다.
