# 브랜치 병합 시 변경 보존 절차

> 보관 문서입니다. 현재 기준은 [소프트웨어 변경·검증 기준](../../../knowledge/rules/coding/engineering-changes.md)에 통합했습니다. 아래 내용은 과거 기준이며 활성 규칙이 아닙니다.

## 준비 조건

현재 요청에서 병합이 허용된 대상·기준 브랜치와 프로젝트 Git 운영 기준을 확인한다. 이 문서는 pull·push·merge·배포 권한을 부여하지 않는다. 일반적인 변경 보존·범위 원칙은 [에이전트 사용 기준](../../../AGENTS.md)을 따른다.

## 작업 순서

1. 현재 브랜치와 기준 브랜치의 차이, 작업 트리의 미커밋 변경을 구분한다. 사용자 변경을 병합 작업의 일부로 임의 처리하지 않는다.
2. 충돌한 부분의 양쪽 변경 목적과 연결된 호출·사용처를 읽는다. 한쪽 파일이나 변경을 통째로 선택하는 것으로 충돌 해결을 대신하지 않는다.
3. 두 변경의 필요한 의도를 통합한다. i18n은 양쪽 번역의 추가·수정을 확인한다. 같은 키의 의미가 충돌하면 의미를 확인해 해결한다.
4. rename·파일 교체가 있으면 이전 파일에 들어간 다른 변경도 추적해 새 위치에서 필요한 동작이 보존되는지 확인한다.
5. 기준 브랜치 대비 최종 diff에서 이미 반영된 변경이 새 변경으로 중복 남았는지 확인하고, 통합으로 영향을 받은 경로를 검증한다.

## 완료 기준과 문제 대응

충돌 표시 제거만으로 완료하지 않는다. 양쪽 변경의 의도와 i18n·rename 관련 변경이 최종 결과에 반영됐는지 확인한다. 상충하는 요구를 함께 만족시킬 근거가 없으면 임의로 한쪽을 폐기하지 않고 충돌 지점과 필요한 결정을 보고한다.

## 판단 근거

소유자가 여러 병합 작업에서 반복해서 명시한 양쪽 변경 보존, i18n·rename 처리, 기준 브랜치 변경의 중복 방지 요구를 절차로 구성했고 반영 승인을 받았다. 특정 브랜치명과 개별 작업의 원격 쓰기 승인은 포함하지 않는다.
