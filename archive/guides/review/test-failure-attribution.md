# 테스트·CI 실패의 변경 귀속 확인

> 보관 문서입니다. 현재 기준은 [소프트웨어 변경·검증 기준](../../../knowledge/rules/coding/engineering-changes.md)에 통합했습니다. 아래 내용은 과거 기준이며 활성 규칙이 아닙니다.

## 준비 조건

작업의 기준 커밋·브랜치, 변경 diff, 실패 명령과 로그를 확보한다. 테스트 추가·삭제 판단은 [제품 계약 중심 테스트 기준](../../rules/testing/product-contract-tests.md)을 따른다. 공통 권한·범위·결과 보고 기준은 [에이전트 사용 기준](../../../AGENTS.md)을 참조한다.

## 작업 순서

1. 실패한 검사와 입력·환경·의존성 조건을 확인한다. 원격 CI 실패와 로컬 재현 결과는 구분한다.
2. 변경 코드와 실패 경로를 대조한다. 필요하면 기존 작업을 건드리지 않는 별도 공간에서 기준 커밋에도 같은 조건으로 실패하는지 확인한다. 기준 브랜치 실패라는 이유만으로 같은 원인이라고 단정하지 않는다.
3. 이번 변경으로 발생·악화된 실패, 기준에서도 확인된 기존 실패, 근거 부족으로 미확정인 실패를 구분한다. 비교한 커밋·명령·조건을 근거로 남긴다.
4. 이번 변경에 귀속된 실패는 승인된 범위에서 해결한다. 기존 실패는 무관한 수정으로 확대하지 않고 보고하며, 수정이 필요하면 별도 범위를 정한다.
5. 동일 원인에서 나온 여러 실패는 원인 단위로 묶되 영향받는 검사·경로를 누락하지 않는다. 해결 후 해당 검사를 다시 실행한다.

## 완료 기준과 문제 대응

실패별 귀속 근거, 수정한 범위, 재실행 결과와 남은 차단 사항이 구분돼야 한다. 기준 상태를 재현할 수 없거나 환경 차이를 해소하지 못하면 귀속을 미확정으로 남긴다.

기존 실패라는 판정은 CI 통과나 merge 가능을 뜻하지 않는다. 실제 실패 상태와 프로젝트의 merge 조건을 별도로 확인하고, 검사 우회나 기대값 완화로 성공 처리하지 않는다.

## 판단 근거

소유자가 여러 작업에서 이번 브랜치의 오류와 기존 오류를 구분하도록 지시한 내용, 같은 원인을 여러 문제로 부풀리지 말라는 요구를 바탕으로 구성했다. 비교·귀속 절차는 이를 실행 가능하게 정리한 반영안이며 소유자가 승인했다.
